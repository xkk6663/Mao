## 1. 背景与总体目标

本地 Windows 桌宠（Electron + Live2D）接入小智官方免费云（xiaozhi.me 控制台 / [api.tenclass.net](https://api.tenclass.net)），实现：



* **文字对话**：用户输入文字 → 小智回答（文字 + 官方语音 + 桌宠口型 / 表情联动）

* **图片识别**：截图提问 / 聊天发图 / 屏幕自动观察 → 小智视觉分析 → 返回分析文本 + 语音朗读

* **历史可视化**：长连接以来所有来往记录（文字 / 图片）在聊天界面保留、可回看

* **统一链路**：所有对话、图片识别走同一条小智长连接

硬约束：仅用小智官方免费云，不用付费 API。

## 2. 当前系统架构

### 2.1 组件与链路



```
浏览器（MIO 原版私人空间对话页）
   │  ├─ 文字输入 → WS(role=chat) → 后端 → 官方注入链 → 小智云
   │  ├─ 图片(暂存→发送) → POST /vision → 官方视觉 MCP → 分析文本
   └─ 消息流显示 ← 3s 轮询 /chat-history ← 会话历史(内存+文件)

桌宠主窗（Electron 透明窗）
   └─ WS(role=main) ← 后端广播（官方 TTS PCM / 本地 TTS PCM）→ 播放 + 口型
```

### 2.2 关键机制（现状）



| 机制     | 说明                                                        | 状态        |

## 3. 当前现状分析（问题清单与根因）

### 3.1 【P0】图片识别文本没有声音 / 音色不符

**用户诉求**：图片识别返回的分析文本，希望用**官方小智的音色**朗读出来，而不是本地 TTS 的声音。

**现状**：分析文本当前用 Windows SAPI 本地 TTS 合成后广播给桌宠播放（上轮为解决 "官方注入不稳定 + 角色错乱" 而改的过渡方案）。

**技术根因（为什么不能直接 "用官方音色读任意文本"）**：



* 小智协议中 **TTS 不提供独立合成接口**。官方语音只在 "用户说话 → LLM 回答" 之后自动下发（`type: tts` + opus 音频流）。

* 因此 "让官方音色朗读一段指定文本" 只有间接路径：**把文本当作 "用户说的话" 注入官方** → 官方 ASR 识别 → LLM 回答 → 官方 TTS 播放。这条路径有三个已知不稳定点：

1. **ASR 识别截断**：超过约 60\~150 字的音频识别成功率骤降（实测长音频只回唤醒问候）；

2. **识别误差**：同音字 / 漏字导致回传文本与注入文本不一致（也是角色混淆的根源之一）；

3. **回答内容 ≠ 分析文本**：LLM 是对 "你说的话" 做回应，不会逐字复述，除非提示词要求 "复述原话"。

**结论**：官方协议限制下，"任意文本 + 官方音色" 无法 100% 精确达成；可行的折中方案见 §5.1。

### 3.2 【P0】角色混淆（AI 发出的文字被显示成 "你说"）

**现象**：图片识别流程里，AI 的分析文本（或官方 ASR 回传的注入内容）有时显示成用户发的 "你说"，导致消息流角色错乱、历史记录混乱。

**根因链**：



```
后端把分析文本"注入"官方（模拟用户语音）
   → 官方 ASR 识别这段语音，回传 stt 消息
   → 后端把它写入历史"你说"
   → 当前靠文本匹配（_is_injected_stt：相同/包含）拦截
   → 但 ASR 有识别误差（同音字/漏字/多字）→ 匹配失败 → 写成"你说"
```

**已做过的修复**（仍不够）：



* 注入后 60 秒时间窗口抑制写入；

* 文本相同 / 互相包含 / 前 10 字相同匹配；

* 官方回答回声（LLM 文本被 STT 误收）匹配过滤。

**局限**：所有方案都是 "事后字符串匹配"，ASR 误差一旦超过阈值就漏网。根治需要**机制级解耦**（见 §5.2）。

### 3.3 【P0】图片暂存功能

**用户诉求**：粘贴 / 上传图片后**先暂存在输入框上方**（可预览、可删除），点发送按钮才真正发给小智分析；当前 "选图即发" 不符合预期。

**现状**：注入脚本已改造为暂存模式（粘贴 / 上传 → 缩略图暂存条 → 发送按钮 / Enter 才发送），脚本引用已加版本号强制刷新。后端验证全部就位（新脚本 + 聊天分片图片渲染 + 类名齐全）。

**待确认**：用户浏览器是否完成 "关闭页面重开"（版本号机制需全新加载才生效）。若重开后仍无暂存条，则需进一步排查运行时错误。

### 3.4 【P1】长连接免唤醒（✅ 已解决）

**现状**：已改为 "会话级只唤醒一次"—— 首次注入发一次 "你好"，之后所有对话 / 图片识别不再触发唤醒问候；仅官方断线重连（新会话）才重新唤醒。已提交并重启验证。

### 3.5 【P1】音频断续 / 多回答叠加（大部分已解决）

**已解决**：



* 连续快速发消息互相 abort 吞消息 → 注入串行化锁；

* 多窗口声音叠加 → 音频只广播给 main（桌宠本体）。

**待优化**：官方链路本身偶发卡顿 / 断续（网络、官方服务端），本地 TTS 播放路径已稳定；若最终采用 "官方复述注入" 方案，需配合超时重试与降级策略（见 §5.1）。

### 3.6 【P2】副屏显示（✅ 已解决）



* 跨屏边界脚本 phys\_bounds.ps1 已重建并入 git；

* 桌宠顶部位置放开（可半身出屏），不再松手自动回位；

* 以上改动均已提交 git 管理。

## 5. 技术方案设计（不含源码）

### 5.1 图片识别文本 → "官方音色" 朗读（P0 核心）

三个候选路径，按推荐度排序：

**方案 A：官方复述注入（音色统一，推荐首选）**



* 流程：分析文本 → 注入官方（模拟用户说出 "请用原话复述：<分析文本>"）→ 官方 ASR → LLM 复述 → 官方 TTS 播放。

* 优点：音色 100% 官方；回答带官方表情 / 口型联动。

* 风险：


  * 长文本 ASR 截断 → 注入文本需压短（≤60 字），或**分段注入**（每段 50\~60 字依次注入，连续播放）；

  * LLM 复述有轻度改写（内容大意一致，非逐字）；

  * 需配合 "注入回声过滤"（见 5.2）防止复述文本被误写 "你说"。

* 降级：注入失败 / 超时 → 自动回退本地 TTS（方案 C）播放原分析文本，保证一定有声音。

**方案 B：官方上下文 + 本地朗读（音色妥协，最稳）**



* 流程：分析文本**仍注入官方**（让官方知道图片内容、维持上下文），但**语音播放用本地 TTS**（分析文本 + 官方回答都本地读，或只读分析文本）。

* 优点：链路简单、稳定、长文本完整；官方上下文不丢。

* 缺点：音色为本地合成（可通过 SAPI 选择中文女声尽量接近官方音色，但无法完全一致）。

**方案 C：本地 TTS 调音色（纯本地，零官方依赖）**



* 现状即此方案；优化点为选择更接近的 SAPI 音色（如 Huihui / Yaoyao 等中文女声）、语速 / 语调调节。

* 优点：100% 稳定可控；缺点：音色始终有差异。

**推荐**：先实现**方案 A + C 自动降级**（A 成功用官方音色；A 失败回退 C，保证 "一定有声音"）。若用户对复述改写的容忍度低，可退到方案 B。

### 5.2 角色混淆根治（P0）—— 机制级解耦

**核心思路：把 "谁在说话" 从依赖官方 STT 改成由系统主动标记。**



1. **用户消息（浏览器输入）**：前端发送时由后端**直接写 "你说" 历史**（当前已是，保留）；

2. **AI 消息（官方回答 / 图片分析文本）**：由后端**直接写 "她说" 历史**（当前已是，保留）；

3. **官方 STT 回传消息：一律不再写历史**。STT 只用于：更新唤醒 / 活跃状态、判断注入是否被识别（用于重试），**不进入消息流、不写 "你说"**。

效果：



* 注入的分析文本 / 官方复述即使被 STT 识别回传，也不会出现在消息流（从机制上杜绝 "你说 \[分析]"）；

* 官方误听环境声也不再污染历史；

* 消息流中的 "你说" 只有用户真实输入一种来源，"她说" 只有 AI 输出一种来源。

代价：聊天历史中不再包含 "官方 ASR 听懂了什么" 这类中间信息（对用户无价值，可接受）。

### 5.3 图片暂存（P0）

**交互定义（待用户确认后按此实现 / 修复）**：



1. 粘贴（Ctrl+V）或点 📷 选图 → 图片以缩略图显示在输入框上方（可多张，各带 ✕ 删除）；

2. 输入框可同时输入文字（将作为图片提问附带文字）；

3. 点发送按钮或 Enter → 图片 + 附带文字一起发送给小智分析 → 发送后暂存区清空；

4. 无暂存图片时，发送按钮 / Enter 走普通文字对话。

**现状**：代码已实现该交互；待确认 "关闭页面重开" 后是否生效（版本号 v20261012b）。若仍失效，排查路径：浏览器控制台报错 → 注入脚本是否执行 → 暂存条容器是否被 Vue 重渲染清理。

### 5.4 音频链路稳定（P1，配合方案 A 实施）



* 注入串行化锁保留（已解决吞消息）；

* 方案 A 增加：注入前先 abort 打断旧会话、单次注入超时重试一次、连续多段注入间留 0.5\~1s 间隔；

* 监听后端日志（已启用 python -u 实时落盘），出现 "本地语音播放失败 / 注入失败" 即自动降级切换。

## 7. 建议实施顺序与验收标准

### 实施顺序（按依赖与收益）



1. **角色解耦**（§5.2）—— 改动小、机制级根治，先做（为方案 A 铺路，杜绝复述文本错乱）；

2. **图片识别 → 方案 A + C 降级**（§5.1）—— 音色统一 + 一定有声音；

3. **图片暂存确认 / 修复**（§5.3）—— 用户 "关闭重开" 后验证，失效则查运行时；

4. 音频稳定性回归测试（连续对话、连续发图、观察触发）。

### 验收标准



* [ ] 发图分析：能听到**官方音色**朗读分析文本（失败时自动降级本地语音，但一定有声音）；

* [ ] 消息流：分析文本只显示 "她说"，绝不出现 "你说 \[分析文本]"；连续 10 次发图无角色错乱；

* [ ] 粘贴 / 上传图片：先出现暂存缩略图，点发送才发送；

* [ ] 长连接期间多次对话 / 发图：不出现 "你好 / 你来啦" 唤醒问候（除非断线重连）；

* [ ] 聊天界面历史完整保留文字 / 图片，刷新后可见。
